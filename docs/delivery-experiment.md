# 配送路線：邏輯堆疊是否有實際效益？

此實驗比較單一汽車的六站配送更新策略。公開地標附近的座標是合成示範，未確認可停車或交貨入口。沒有串接真實顧客、定位、派單或導航。

## 在本機試用

啟動 Studio 後開啟 `/delivery`。先以固定矩陣試用，或選 OSRM 按「更新路網並規劃」。OSRM 回傳道路車程與形狀；抓取時間不是道路資料更新時間，也不代表即時車流。Google 模式需伺服器的 `GOOGLE_MAPS_API_KEY`，只顯示當次交通估時及路線清單，不疊 OSM、不保存比較快照、不匯出 Google 原始結果。

時鐘、時間窗、服務時間與容量都能修改。單一車輛在起點裝載全部需求，按最早/最晚開始服務時間規劃，可選擇回倉。最多七站，精確枚舉所有排列（最多 5040），依序最小化逾時站數、逾時分鐘、總耗時、距離。超載、無路徑及不可能的時間窗必須明示；不可把最少違規路線當成可行方案。每段距離和車程使用同一方向矩陣，不把直線距離冒充道路。

## 四個比較策略

1. 每則訊息都重算：每個事件觸發同一求解器。
2. 規則與內容去重：明確欄位變動必定重算，相同內容與狀態不重算；新的自由文字保守重算。
3. 單層 JEV：在相同去重規則後，問這則訊息是否需要重新檢查本趟配送。
4. 雙判斷 + AND：獨立判斷「與本趟範圍相關」及「有實質配送變動」，再用三值 AND 組合。

語意問題每次同批提交；堆疊版本問兩題，單層問一題。UNKNOWN 與提供者失敗保守重算；失敗後不重試，停止該策略的後續模型呼叫。明確欄位變動不會被模型否決。文字不會自動轉成新的座標或期限；要確認後透過結構化更新才能改變計畫。

所有策略使用相同矩陣快照、相同事件及相同求解器。比較不會按策略額外呼叫地圖，不能以此報告宣稱已實際省掉若干次已付費請求。初始規劃亦計入各策略。快照只在本機記憶體保存十分鐘，最多十二筆；Google 不進入此快照庫。

## 量測與限制

分別記錄實際模型請求嘗試、問題數、語意評估經過時間、同步求解經過時間、建議刷新次數、漏處理教學事件及不必要刷新。OSRM 取得矩陣與幾何的呼叫獨立記錄；快取命中為零次外呼。模型健康檢查不當作推論。

成本為可調單價的情境估計：每次建議刷新假設有一個完整矩陣請求與一個路線形狀請求，矩陣含 N×N 元素。使用者自行決定哪些計費項目單價為零；沒有填全單價時，不輸出金額。同步求解的經過時間不是 CPU 用量，沒有量測能源、硬體折舊、雲端實際帳單或司機實際送達。

內建六則事件與預期刷新標記僅為作者提供的教學案例，沒有獨立人工標註。Fixture 直接從標記產生測試分數，屬刻意示範，不能當作準確率。修改任何配送設定或事件後，失去對應教學標記的項目不計品質分數。語意策略執行順序以事件雜湊決定並記錄，單次量測仍受模型暖機與固定策略順序影響。

LocalJev 是本機生成模型的 JEV 相容橋接服務，與官方 TypeSafe Jev 不同。模型、門檻及案例均須報告，不能把本機結果外推成官方成本/速度。此展示沒有獨立保留測試集、完整消融或跨地區驗證，不能宣稱堆疊必然更準確、更便宜或已實現 AGI。

## 本輪事先固定的示範設定

- 場景：`workbench/delivery-scenario.json`。
- 共同 FALSE / TRUE 門檻：0.2 / 0.8；尚未校準。
- 模型：LocalJev localjev-0.2，上游模型須由實際回應/服務資訊確認；TypeSafe 只有明確選擇才使用。
- 每輪最多六則事件；相同訊息去重；每個新自由文字各對單層與雙判斷做一次批次推論；沒有自動重試。
- 評估重點：與規則基準比較，而不只與每次重算比較。漏掉相關事件不能被省錢指標抵銷。
- 假設費率預設全部未填；不假造零成本或節省率。

## 已觀察到的結果

本機一次試跑中，規則版本6次建議刷新、單層及雙判斷皆4次，但語意處理各增加約19秒，規則求解只有毫秒；雙判斷題數是單層兩倍，決策相同。本輪尚未證明邏輯堆疊比單層更有效，亦未證明實際金額節省。原始紀錄與限制見[配送實測](../eval/delivery/README.md)。
